# 游戏数据与脚本

[返回文档目录](README.md)

服务端运行行为不仅由 Java 代码决定。仓库中的 WZ XML 和 JavaScript 脚本是受版本控制的核心运行输入，修改后必须单独验证。

## WZ XML 数据

WZ 数据位于 `wz/`，按原始 WZ 文件分类：

```text
Base.wz       Character.wz  Effect.wz   Etc.wz
Item.wz       Map.wz        Mob.wz      Morph.wz
Npc.wz        Quest.wz      Reactor.wz  Skill.wz
Sound.wz      String.wz     TamingMob.wz UI.wz
```

当前 Java 服务端主要加载角色、其他配置、道具、地图、怪物、NPC、任务、反应堆、技能和字符串等数据。部分目录虽然在仓库中存在，但当前 `WzData` 枚举没有主动加载；修改前应搜索实际引用，不要仅根据目录名判断是否生效。

## WZ 路径

源码读取系统属性：

```text
wz.path
```

默认值是：

```text
wz
```

因此从仓库根目录启动时通常不需要额外参数。显式指定时使用：

```text
-Dwz.path=/实际路径/wz
```

不要使用历史写法 `-Dwzpath=...` 期待改变目录；当前源码不会读取该属性。

## 修改 WZ XML

修改前先确定：

- 对应数据由哪个 `*.wz` 目录提供；
- Java 代码使用的是数字 ID、节点名还是字符串路径；
- XML 中同一级是否允许同名节点；
- 修改是替换值、新增节点还是删除节点；
- 数据是否已经被服务端缓存在内存中。

`WzData.load()` 可以重新解析已修改内容，但源码明确提示：新增、删除文件或删除既有内容时，不保证热重载结果正确。涉及结构变化时应完整重启服务端。

不要使用普通 XML 工具自动重排全部文件。大规模格式化可能产生巨量无意义差异，也可能改变旧数据解析依赖的顺序、重复节点或编码。

## JavaScript 脚本

脚本位于：

```text
scripts/npc
scripts/events
scripts/quests
scripts/portals
scripts/reactors
```

这些脚本由 Java 8 的 JavaScript 引擎加载，可能通过注入对象调用 Java 服务端 API。一个脚本能够通过语法编译，不代表它引用的 NPC、地图、任务、道具或 Java 方法在运行时一定存在。

## 脚本文件定位

常见规则包括：

- NPC 脚本按 NPC ID 或带分支后缀的文件名查找；
- 任务脚本按任务 ID 查找；
- 传送点脚本按脚本名查找；
- 事件和反应堆由对应管理器按配置或数据引用加载。

新增脚本前应先搜索同类脚本和管理器代码，确认文件名、函数入口、返回约定和可用上下文对象。

## 编码和换行

仓库数据校验以 UTF-8 读取 JavaScript，WZ XML 也按 XML 内容解析。编辑时应：

- 保持 UTF-8；
- 避免混入不可见控制字符；
- 不要无意转换全部行尾；
- 保持中文文件夹名称；
- 对模板字符串、反斜杠和引号特别谨慎；
- 不把编辑器临时文件、备份文件或 `.orig` 文件加入仓库。

## 自动校验

只校验脚本、WZ 和配置：

```bash
./mvnw --batch-mode --no-transfer-progress \
  -Dtest=RepositoryDataValidationTest test
```

Windows：

```powershell
mvnw.cmd --batch-mode --no-transfer-progress -Dtest=RepositoryDataValidationTest test
```

该测试会：

1. 编译所有 `scripts/**/*.js`；
2. 安全解析所有 `wz/**/*.xml`，禁用外部实体和外部 DTD；
3. 检查服务端配置的必需键、重复键和数值范围。

配置校验把 `;` 开头行视为注释，但运行时使用的 Java `Properties.load` 并不把 `;` 视为标准注释前缀；校验也不会发现逗号列表内部的重复事件名或 ID。这两点应在配置评审中人工检查。

失败输出最多集中报告一部分文件，应先修复最早的共同根因，再重新运行，不要只处理最后一个文件。

## 自动校验没有覆盖的内容

数据测试不会证明：

- 脚本引用的 Java 方法一定存在；
- 某个 NPC 对话分支可以完整走通；
- 地图、怪物、道具和任务 ID 之间的业务关系正确；
- 数据库已经包含脚本依赖的数据；
- 热重载后缓存已经正确清理；
- 客户端显示和服务端数据完全一致；
- 修改没有破坏游戏经济或权限边界。

高风险修改还应在隔离数据库和测试账号中执行真实流程验证。

## 修改后的验证建议

### NPC、任务和事件脚本

1. 运行脚本编译校验；
2. 确认引用的 ID 和 Java API；
3. 使用隔离测试角色触发入口；
4. 走完成功、取消、背包满、余额不足等分支；
5. 检查数据库和日志；
6. 重启后再次验证持久化状态。

### 地图、怪物和掉落数据

1. 运行 WZ XML 校验；
2. 检查对应 Java 工厂和缓存；
3. 完整重启服务端；
4. 进入目标地图验证生成、掉落和离开流程；
5. 检查是否影响其他共享模板或 ID。

### 道具和商城数据

同时检查：

- WZ Item/String 数据；
- 数据库中的现金道具或商店数据；
- Java 道具模型和数据包；
- 数量、有效期、唯一标识和交易限制；
- 重复领取、重复扣款和异常重连场景。

## 安全边界

WZ 和脚本可以影响服务端资源消耗、数据库写入和玩家资产。审查时要关注：

- 不可信参数的长度、范围和所有权；
- SQL 或命令拼接；
- 无限循环、无限生成和无上限集合；
- 重复结算、复制道具和部分写入；
- GM 或管理员能力是否被普通玩家触发；
- 脚本是否读取运行主机上的非项目文件。

发现安全问题时按 [`SECURITY.md`](../SECURITY.md) 私密报告。
